# changelog -- 결과 보고 형식

`/changelog` 스킬(`skills/changelog/SKILL.md`)의 절차 3(분류) 이후, 채팅에 출력할 최종 형식을 정의한다. 파일로 저장하지 않고 이 형식 그대로 채팅 응답에 출력한다. 아래 한글 헤더·문구는 예시이며, 실제 출력은 대화가 진행 중인 언어로 옮겨 쓴다.

## 헤더

범위를 한 줄로 밝힌다:

```
## 변경사항 (<BASE> → <HEAD 앞 7자리>)
```

`BASE`는 스크립트가 출력한 `BASE:` 값(태그명 또는 사용자가 지정한 ref)을 그대로 쓴다.

## 카테고리별 목록

절차 3에서 분류한 카테고리 순서대로(신기능 → 버그수정 → 개선 → 서브모듈 업데이트 → 기타), 항목이 있는 카테고리만 아래처럼 출력한다:

```
### 신기능
- (변경 요약)
- (변경 요약)

### 버그수정
- (변경 요약)
```

- **각 항목은 한 줄 불릿, 커밋이 아니라 diff에 남은 최종 변경 단위 기준**. 커밋 메시지를 그대로 나열하지 말고, diff 내용을 근거로 **무엇이 어떻게 바뀌었는지 사용자 관점에서** 서술한다.
  - 좋은 예: `- 저장소 목록에서 특정 이름/경로를 자연어로 지정해 대상만 골라 pull할 수 있게 함`
  - 나쁜 예 (커밋 메시지 그대로): `- feat(pull): add natural-language [<target>] argument`
- 논리적으로 같은 변경을 여러 커밋(수정 후 재수정 등)이 나눠 담고 있으면 하나의 항목으로 합친다.
- **범위 안에서 추가됐다가 제거되는 등 되돌려져 diff에 순변화로 남지 않은 내용은 아예 쓰지 않는다** — 커밋 로그에만 존재하고 최종 diff에는 없는 변경은 사용자가 알 필요가 없다.
- **범위 중간에 도입된 뒤 다시 수정된 기능은, 그 중간 과정이 아니라 diff에 남은 최종 모습만으로 서술한다.** "이전에 추가한 X를 Y로 수정함"처럼 이 범위 안의 과거 상태를 언급하지 말고, 마치 처음부터 그 모습으로 나온 새 변경인 것처럼 소개한다.
  - 좋은 예 (기능이 범위 중간에 A로 추가됐다가 B로 재작업된 경우): `- 설정 값을 파일로 저장하는 기능 추가`
  - 나쁜 예 (중간 과정 언급): `- 설정 값 저장 방식을 메모리 캐시에서 파일 저장으로 변경`
- 커밋 해시는 본문에 포함하지 않는다.

### 서브모듈 업데이트

절차 3에서 "영향 있음"으로 판단된 서브모듈만 포함한다. 서브모듈 경로를 함께 표시:

```
### 서브모듈 업데이트
- **<서브모듈 경로>**: (내부 변경 요약, 신기능/버그수정/개선 중 해당하는 내용 위주로)
```

`SUBMODULE_UNAVAILABLE`인 서브모듈은 이 섹션에 아래처럼 짧게만 표시한다:

```
- **<서브모듈 경로>**: 업데이트 있음 (세부 커밋 확인 불가)
```

### 기타

문서/내부 리팩터링/빌드 설정 등 사용자 영향이 낮은 변경은 짧은 불릿 목록으로 끝에 모은다. 항목 수를 임의로 추리거나 "그 외 N건"으로 뭉뚱그리지 말고, 최종 diff에 남은 변경은 전부 목록에 포함한다.

## 빈 범위 처리

절차 2의 `COMMITS_START`~`COMMITS_END` 사이에 커밋이 없고 모든 서브모듈도 영향 없음으로 판단되면, 카테고리 목록 대신 "지정한 범위에 사용자에게 영향을 주는 변경사항이 없습니다"라고만 짧게 답한다.
