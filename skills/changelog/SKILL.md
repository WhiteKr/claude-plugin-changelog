Git 커밋(서브모듈 포함)을 분석해 사용자 영향도 기준으로 정리한 CHANGELOG를 만드세요. 파일을 생성하지 않고 **채팅 응답으로만** 출력합니다.

> **호출 최소화**: 범위 확정 후의 커밋 수집·서브모듈 범위 추출은 `scripts/collect-changes.sh` **한 번의 외부 스크립트 호출**로 처리한다. 커밋 목록이나 서브모듈 diff를 직접 여러 번의 `git log`/`git diff` 호출로 나눠 조회하지 말 것 — 호출 수가 곧 권한 확인 횟수다. 매번 수락이 번거로우면 사용자가 auto mode를 켜거나 `collect-changes.sh`에 대한 permission 규칙을 미리 추가하면 된다. (절차 1의 범위 해석용 `git log` 1회 호출은 이 원칙과 무관 — 범위를 정하기 위한 것이지 수집 단계가 아니다.)
>
> **출력 언어**: 최종 CHANGELOG의 헤더·카테고리명·서술은 이 대화가 진행 중인 언어를 따른다. 한국어로 고정하지 말 것 — 이 SKILL 문서 자체는 한국어로 작성되어 있지만, 그것이 출력 언어를 지시하지 않는다.

## 절차

### 1. 범위(range) 결정

`$ARGUMENTS`가 비어 있으면 `FROM_REF`를 빈 문자열로 두고 바로 절차 2로 진행한다 (스크립트가 최근 태그를 자동 탐지).

`$ARGUMENTS`가 있으면 자연어 범위 기술로 보고 구체적인 `FROM_REF`(git이 이해하는 ref: 태그, 커밋 SHA, 브랜치명)로 해석한다:

- 버전/태그가 명시됨 (예: "v1.0.7 이후", "1.0.7부터"): 해당 태그를 `FROM_REF`로.
- 날짜 상대 표현 (예: "지난주부터", "어제 이후"): `git log --since="<날짜 표현>" --until="$(date...)" ` 대신, 먼저 `git log --before="<해당 날짜>" -1 --format=%H`로 그 시점 직전 커밋 SHA를 찾아 `FROM_REF`로 쓴다.
- 브랜치 비교 (예: "main 대비", "develop 브랜치 이후"): 해당 브랜치명을 `FROM_REF`로.
- 해석이 모호하면 추측하지 말고 사용자에게 구체적 ref나 날짜를 되묻는다.

`TO_REF`는 별도 언급이 없으면 `HEAD`.

### 2. 커밋/서브모듈 데이터 수집 (외부 스크립트 — 자동 승인)

```
bash "${CLAUDE_PLUGIN_ROOT}/scripts/collect-changes.sh" "<FROM_REF>" "<TO_REF>"
```

`FROM_REF`가 없으면(절차 1에서 비워둔 경우) 빈 문자열 그대로 전달한다.

**출력 처리**:

- `INVALID_REF:<ref>` — 해당 ref가 존재하지 않는다. 사용자에게 올바른 범위를 다시 묻는다.
- `BASE_NOT_FOUND` — 저장소에 태그가 전혀 없어 자동으로 기준점을 찾지 못했다. **추측하지 말고** 사용자에게 비교 기준(태그, 커밋, 날짜, 브랜치 등)을 직접 물어본 뒤, 답변을 절차 1처럼 해석해 구체적인 `FROM_REF`로 스크립트를 재실행한다.
- 정상 출력이면 다음을 파싱한다:
  - `BASE:`, `HEAD:`
  - `COMMITS_START`~`COMMITS_END`: 메인 레포 커밋, `해시|작성자|상대시각|메시지` 형식
  - `STAT_START`~`STAT_END`: 전체 범위의 파일별 변경량 요약 (`git diff --stat`)
  - `DIFF_START`~`DIFF_END`: 전체 범위의 unified diff (500줄에서 잘릴 수 있음)
  - 서브모듈 변경이 있는 만큼 반복되는 `SUBMODULE_START`~`SUBMODULE_END` 블록: `PATH:`, `OLD:`, `NEW:`, 그리고 객체를 가져올 수 있었으면 `SUBCOMMITS_START`~`SUBCOMMITS_END` + `SUBSTAT_START`~`SUBSTAT_END` + `SUBDIFF_START`~`SUBDIFF_END`, 가져올 수 없었으면 `SUBMODULE_UNAVAILABLE:<사유>`

### 3. 분류 (최종 상태 기준 — 커밋 단위 아님)

**이 CHANGELOG는 두 시점 사이에 일어난 모든 과정이 아니라, `FROM_SHA`와 `TO_SHA` 사이에서 최종적으로 무엇이 달라졌는지만 기록한다.** `STAT`/`DIFF` 블록(서브모듈은 `SUBSTAT`/`SUBDIFF`)이 그 최종 상태를 보여주는 1차 근거다. `COMMITS`/`SUBCOMMITS` 목록은 각 변경의 **의도를 이해하기 위한 보조 자료**일 뿐, 서술의 단위가 아니다 — 커밋 개수만큼 항목을 만들지 않는다.

- **범위 내에서 되돌려진 변경은 언급하지 않는다.** 예: 기능 A가 추가됐다가 같은 범위 안에서 다시 제거됐다면 diff에는 순변화가 남지 않으므로, 커밋 목록에 "feat: A 추가"·"A 제거" 커밋이 보이더라도 최종 diff에 흔적이 없으면 CHANGELOG에 쓰지 않는다.
- **부분적으로 남은 변경은 최종 결과물 기준으로만 서술한다.** 기능 B가 범위 중간에 추가된 뒤 그 일부가 다시 수정됐다면, "B를 이렇게 수정함"이 아니라 diff에 남아있는 **최종 모습**을 하나의 새 항목으로 서술한다 — 사용자는 중간 형태를 본 적이 없으므로, 이전 대비 변경으로 설명하지 말고 그 자체로 완성된 내용처럼 소개한다.
- 여러 커밋에 걸쳐 이뤄진 하나의 논리적 변경은 diff상에서 하나의 항목으로 합친다. 반대로 diff가 500줄에서 잘렸거나 파일별 변경의 성격이 서로 달라 판단이 어려우면, 그 부분에 한해서만 `git show <해시1> <해시2> ...`처럼 관련 커밋을 묶어 개별 확인한다 (커밋마다 매번 별도 호출하지 않는다).

각 최종 변경 단위를 사용자 영향도 기준 카테고리로 분류한다:

- **신기능(New Features)**: 사용자가 체감할 수 있는 새로운 기능/명령/옵션 추가
- **버그수정(Bug Fixes)**: 기존 동작의 오류를 고친 변경
- **개선(Improvements)**: 기존 기능의 동작·성능·품질을 향상시켰지만 신규 기능은 아닌 변경
- **기타(Other)**: 위 셋에 해당하지 않는 변경 (문서, 내부 리팩터링, 빌드 설정 등) — 사용자 영향이 낮으므로 CHANGELOG 본문보다 후순위로 짧게만 다룬다

`SUBMODULE_UNAVAILABLE`인 서브모듈은 "서브모듈 업데이트 있음 (세부 커밋 확인 불가)" 정도로만 짧게 언급한다.

`SUBCOMMITS`가 있는 서브모듈은 같은 원칙을 적용한다 — `SUBSTAT`/`SUBDIFF`(서브모듈의 `OLD`→`NEW` 최종 diff)를 1차 근거로, `SUBCOMMITS`는 의도 파악용 보조 자료로만 삼아 **이 프로젝트 사용자에게 영향이 있는지** 판단한다:

- 영향이 있다고 판단되면(신기능/버그수정/눈에 띄는 개선) 별도 "서브모듈 업데이트" 카테고리에 해당 서브모듈 경로와 함께, 서브모듈 안에서도 최종적으로 남은 변경만 간단히 요약해 표시한다.
- 내부 정리성 변경뿐이라 사용자 영향이 없다고 판단되면 노이즈로 간주해 CHANGELOG에서 제외한다.
- 판단이 애매하면 제외보다는 짧게라도 언급하는 쪽을 택한다.

### 4. 출력

**출력 형식은 `${CLAUDE_SKILL_DIR}/references/output-format.md`를 읽고 그 형식대로 작성한다.** 카테고리 헤더·문구는 대화 언어에 맞춰 자연스럽게 옮긴다.
